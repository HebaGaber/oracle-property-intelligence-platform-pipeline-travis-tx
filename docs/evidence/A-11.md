## What was built

1. **Run 1 publication**: the full Travis County dataset built into two data groups — `county` (TCAD roll, R-subtype only, 441,961 rows) and `property_improvement` (Austin permits, roofing-classified with a decided status only, 17,387 rows) — hashed and validated through `elephant-cli` into 12 CARs (10 county batches + 2 permits batches), exported to normalized tables (204 table parts), assembled into a single `RunManifestV1` via the real `buildManifest()` (widened during this story to sum rows across N batches per group — RL 19:30), and uploaded to Filebase.
2. **Run 1 manifest**: CID `bafkreiddef7ssybq6m4wpmah7adposaxbiawaxcmqndzk36wyhd7k4h6gu`, 228 artifacts (12 car + 12 directory + 204 table parts), 2,836,632,126 bytes (≈2.64 GiB). `previousManifestCid: null` (Run 1 starts a new chain, per D-2(a)).
3. **GitHub Release** (durability backup, 12 CARs): https://github.com/HebaGaber/oracle-property-intelligence-platform-pipeline-travis-tx/releases/tag/run1-travis-full-20261023
4. **AM-05 additive carCid uploads**: all 24 `carCid` artifacts (12 CAR files + 12 `tables.car` index files) uploaded to Filebase as plain raw-leaves files, not just `dag/import`ed — required for gateway-level verification of the CAR bytes themselves, not just the DAG root.
5. **Scheduler (AC-12, A-12 scope)**: an ECS/Scheduler stack deployed to AWS `eu-north-1`, account `515618610572`, schedule `countylens-incremental-run` created and confirmed `State: DISABLED`. No one has enabled it; it costs nothing while disabled.
6. **Second-pin investigation (AD-22)**: Pinata was tested as a genuine second storage pin and found non-viable on the free plan — `pinByHash` (pin-by-CID) 403s with `PAID_FEATURE_ONLY`; the fallback `pinFileToIPFS` assigns its own unrelated CID to raw CAR bytes (not the CAR's embedded root CID) and fails outright on large (~220MB) files. User decision: skip the second pin for Run 1; durability is Filebase (primary pin) + GitHub Release (CARs, re-pinnable backup) + two-gateway verify (Pinata gateway + Filebase gateway, read-only).

### Two defects found in Run 1

1. **Permits never joined county properties.** On the hosted Permits page: 0 rows loaded of 17,387. In DuckDB, `meta.permit` = 0 because no `property_has_property_improvement.from_cid` equalled any `county.property.cid` (10,867 of 10,867 unmatched).

### Root cause and fix commits

- Defect 1: the county path built the shared files (`property.json` etc.) from the full export record; the permits path rebuilt them from the Query DB's slim `parcels.payload_redacted`, which lacked the legal description and improvements, never passed the recorded year built, and skipped the assembled-coordinate geometry override. Fixed by one shared builder for both groups.
- Defect 2: the transform emitted the profile's `trade_permit` verdict rows. Fixed by skipping them as `trade_sub_permit` (counted as excluded, kept in the internal ledger).
