## What the pilot is (and is not)

The pilot is **a schema contract, not a distribution**. Its permit slice was chosen by PO decision
D-3 (42 Austin permits issued in 2026-09, 5 Expired BP permits and 3 older Final BP permits), so it
is skewed to open permits and to recent work. Do not read rates, shares or averages from the
sample or the pilot views: they show the shape of every column and every missing reason, not how
often each value occurs in Travis County.

## Status rule (PO decision D-4a): empty status means stalled

The lexicon `improvement_status` enum has no Expired value. An Expired Austin permit is published
with `improvement_status` **null**, and the views read **empty status means stalled**: a null
`improvement_status` on a published permit with an `issue_date` gives `status_class = 'stalled'`.
Permitted, Planned and OnHold give `open`; Completed gives `closed`. The mapping is generated from
the profile (`profiles/travis-austin@1.0.0`, `packages/query-core/generated/travis-austin@1.0.0.status-map.sql`)
and is keyed on (jurisdiction, `improvement_status`): the rule applies only for the profile's jurisdictions
(`austin`, from the request host of `source_http_request`). Excluded and needs_review permits are
never published, so the views carry no status filter of their own. Every row lists
`{field: "status_raw", reason: "no_lexicon_carrier"}` and `{field: "expiry_date", reason: "no_lexicon_carrier"}`
in `missing`, and a stalled row's null `improvement_status` is listed with `enum_lacks_value`
(the carrier exists; its enum has no value for the source word).

`status_class` is never silently empty: when it cannot be derived (a null status from another
jurisdiction, a null status without an issue date, or a lexicon value the profile does not map,
such as InProgress) it is null and the row lists `{field: "status_class", reason: "needs_review"}`;
`final_date` and `open_days` then also give `needs_review`, and a null `improvement_status`
gives `needs_review` instead of `enum_lacks_value`.

**Open duration (ERR-70).** `status_class` is the class of the source status; it does not say the
work is still going. An Austin permit with status Expired (stalled) very often has a `final_date`:
the work was finished and the permit lapsed administratively. `open_days` (as_of − issue_date) is
therefore counted only for an open or stalled permit with **no** `final_date`. A plausible
`final_date` (not before `issue_date`, not after `as_of`) gives `open_days` null with reason
`not_open`; a `final_date` before `issue_date` or after `as_of` is a data-quality gap and gives
`open_days` null with reason `needs_review`. A long-open lead is `open_days` above the threshold;
`is_open` still mirrors `status_class = 'open'`.

**For raw-table consumers** (reading `property_improvement` Parquet without these views): a Travis
permit whose `improvement_status` is null, whose `source_http_request` host is an Austin host
(`data.austintexas.gov`, `abc.austintexas.gov`) and which has a `permit_issue_date` is an
**Expired (stalled)** permit, not a permit with an unknown status. Any other null status is unknown.

## Location, ZIP search and value

The Travis export reaches a property's point only through **property_has_parcel → parcel_has_geometry → geometry**
(the TCAD point). There is no `address_has_geometry` and no `property_has_tax` in the export, and
`address` properties are not emitted, so there is no situs text, situs ZIP or owner mailing
address in v1. A ZIP or place search therefore uses the travis-places gazetteer point of the ZIP
or place and a bounding box around it over `latitude`/`longitude`; it never matches a ZIP
column. Market value is absent: no assessed or market value is published in v1.

## Roof date

`roof_date` is the latest accepted terminal date (`completion_date` or `permit_close_date`, not
after `as_of`, not before the issue date) of a **closed** Roofing permit linked to the property
(Replacement → basis `permit`, confidence high; else New → `new_construction`, medium), read
from the published permit rows. Otherwise it is `structure.roof_date`, which carries only the
TCAD built year (basis `built_year`, confidence low); a permit-derived date is never written on
`structure` with the TCAD request. An open or stalled replacement never resets the roof age
(P0-8). These rules are the kit roof-age estimator's, and the pilot views agree with its ledger
for every property. The estimator saw a slice of each parcel's Austin permits, not its full
history (caveat `partial_history`, in the manifest).

## Owner

The current owners are read through the property: the persons and companies linked to it by
`person_has_property` and `company_has_property` (ERR-69), independent of any sale, so a
property with no dated sale still has an owner. `owner_kind` is `company` when any company is
linked, else `person`, else `unknown`; `owner_name` lists the persons (by last, first name) and
then the companies (by name), each once, separated by `; `. A property with no owner lists
`owner_unparsed`, `owner_confidential` (TCAD confidentiality flag, P0-15) or `no_owner_record`,
read from the manifest `coverage` counts `owner_unparsed`, `owner_confidential` and
`owner_no_record` (when more than one is non-zero the row cannot be told apart and lists
`needs_review`). `no_dated_sale` is a tenure reason only. A run written before Run 3 has no
property-owner edges: its current owners are the persons and companies of the latest dated sale
(the latest dated sale is the current owner), so the same rows keep reading.

## Contractor

`contractor_resolution` is `resolved` only when the permit has exactly one
`property_improvement_has_contractor` edge; with several edges no company is picked: the row is
`unresolved` and lists `{field: "contractor_company_cid", reason: "needs_review"}`. The AD-24
five-state totals (`contractor_resolved`, `contractor_candidate`, `contractor_ambiguous`,
`contractor_conflicting`, `contractor_unresolved`) are in the manifest `coverage`.

### v1.1 (additive): contractor as printed and BBB search link

Backward compatible: every v1 column keeps its name and type; the new columns are nullable and a
run published before Run 3 binds them as null with a reason. The permit's printed contractor
**company** name is published as `company.name`, linked by `property_improvement_has_contractor`,
with the permit's own request as provenance and **no** `sunbiz_document_number` (PO decision
2026-10-25). It is **as printed, unverified**: a name is evidence, not identity, so
`contractor_resolution` stays `unresolved` (it becomes `resolved` only when the company carries an
official registry id, which no Austin permit prints). No person, phone or address is published; a
permit that prints only a person name has no contractor.

On `v_roofing_permit`: `contractor_name_as_printed` (the company name, null with
`contractor_unresolved`), `bbb_status` = `blocked` with `bbb_status_reason` = `bbb_blocked` when a
name exists (else `not_checked` / `contractor_unresolved`), `bbb_rating` always null (missing
reason `bbb_blocked`; the UI says "BBB rating not published (BBB blocked the lookup)"), and `bbb_url`,
a BBB **search** link built in the view from the name and the city Austin (UI text "Search BBB for this
contractor"; null with `source_missing` when there is no name). The link is never fetched
(A-01: HTTP 403 challenge); its shape is **unverified until a human clicks one example**.
`contractor_company_cid` now means the company as printed. `contractor_name_raw` is replaced by
`contractor_name_as_printed`. Not published (still `no_lexicon_carrier`): `status_raw`,
`expiry_date`. Details: `docs/defects/ERR-66-contractor-name-and-bbb-link-missing.md`.

## Manifest coverage and profiles for consumers

`coverage.parcels_published` (`published_rows`) is the number of County `property` rows the run
publishes; its `note` states the basis (real-property accounts only). The builder refuses a
manifest whose count differs from the published county part row counts, like
`permits_emitted`. A manifest without the key (Run 1, Run 2) is still valid: read the count from
the tables. The `travis-places` profile names the ZIP area list that classifies
`owner_area_class`. A manifest without it (Run 1, Run 2) means the run declared no area list: the
view then leaves `owner_area_class` `unknown` with reason `out_of_scope` when ZIPs exist, and
`area_list_sha256` is null. Absence means "not published for this run", never an empty list.

## Provenance and `missing`

Every row of `v_property`, `v_roofing_permit` and `v_contractor` carries `cid`, `source_url`,
`captured_at`, `table`, `table_cid`, `run_id`, `manifest_cid`, `as_of` and `missing`.
`missing` holds one `{field, reason}` entry for every null column and every field the contract
cannot carry. Reasons are a closed list: `no_lexicon_carrier`, `not_in_export`, `source_missing`, `no_coordinates`, `no_roof_date`, `basis_unmatched`, `no_dated_sale`, `no_owner_record`, `no_mailing_address`, `zip_not_zcta`, `not_open`, `not_closed`, `contractor_unresolved`, `bbb_blocked`, `bbb_not_found`, `needs_review`, `first_run`, `out_of_scope`, `enum_lacks_value`, `owner_unparsed`, `owner_confidential`.
`v_run` carries the same `missing` list: `previous_manifest_cid` is null on a first run and is
listed as `first_run`; every other `v_run` column is never null.
`captured_at` is source-level: it is the manifest `sources[].captured_at` of the record's source
(the latest successful capture receipt of that source), not a per-record time. `source_url` is
the record's own request URL; when the record has none (or its URL is not a manifest source) it
falls back to the source-level URL of its data group, and no `missing` entry is added because a
URL is present.
In the sample, the property's own provenance is prefixed `property_` (`property_source_url`,
`property_captured_at`, `property_table`, `property_table_cid`, `property_missing`); `run_id`,
`manifest_cid` and `as_of` are the same for both records.

Frozen aliases (the only names that are not lexicon names): `issue_date` = `property_improvement.permit_issue_date`; `final_date` = `property_improvement.completion_date`.

Two further notes from the pilot export:

- **`address` properties are not emitted.** The lexicon `address` class is a top-level `oneOf`,
  and `export-tables` writes only `cid`, `property_cid`, `data_group_cid` and
  `request_identifier` for it. Situs text, city, ZIP and the owner mailing ZIP/state are therefore
  not v1 columns (`not_in_export`); `owner_area_class` is `unknown` and `owner_is_out_of_area`
  is null with reason `not_in_export`. Coordinates come from `geometry` (`coordinate_source = gis_centroid`).
- **`property_cid`** is the property record's CID (`property.cid`, the `from_cid` of every
  `property_has_*` edge). The export's extra column also named `property_cid` is the Seed root
  CID, a different value; it is not used.

## Manifest `car` artifacts: `carCid` (PO decision D-5, 2026-10-21)

Additive, no schema change. A `car` artifact in the run manifest may carry `carCid`: the UnixFS
file CID of the `.car` bytes themselves (raw-leaves CIDv1), because each `.car` file is also added
to IPFS as a plain file. A CAR's own root CID addresses the DAG inside it, not the file, so
`verify-manifest` fetches `carCid` and checks the file's size and SHA-256 against the manifest.
The columns and views above do not change. PO decision D-5, 2026-10-21: "Approve additive carCid
(Recommended)".

## Change rule

Adding a column or an enum member (including a missing reason) is additive and stays in
`contract/v1`. A rename, a retype, or a change of meaning requires `contract/v2`. When the export
starts emitting `address` properties, or the lexicon gains a carrier for a gap above, the field
is added as a new v1 column and leaves the gap list.
