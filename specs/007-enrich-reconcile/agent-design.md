# Agent design: A-07 enrich and reconcile

Read-only design consult, Stage 3 (S3.1). Both agents ran in parallel as Sonnet subagents, read-only, no request to bbb.org, no code written. A third subagent drafted the test cases in parallel (see `testplans/A-07-test-cases.md`).

## oracle (identity, BBB, business/places, reconcile — all four tracks)

**Crosswalk check (decides D-10):** checked `3syk-w9eu` (Issued Construction Permits) via `data.austintexas.gov/api/views/3syk-w9eu.json` full column list — fields are `contractor_trade, contractor_company_name, contractor_full_name, contractor_phone, contractor_address1/2, contractor_city, contractor_zip` plus `applicant_*`. **No license, tax, Sunbiz, Comptroller, taxpayer or registry-ID field exists on this dataset.** Also checked the catalog for any other Austin dataset carrying a contractor identifier: found only the City's ROW Contractor Registry (a PDF, not a Socrata dataset, not an open-data field, and its own city-issued license number, not a Comptroller taxpayer number) and no Socrata "contractor registration" dataset. **Verdict: no official identifier crosswalk exists.** AC-2 is proven only by the labelled unit fixture; record this finding (dataset, URL, full column list, PDF citation) in evidence verbatim — it is the negative finding AC-2 requires.

**Travis-only (342,334) vs statewide (3,487,662) scope:** Travis-only is faster to load and matches the story's stated scope, but understates `candidate`/`ambiguous` if a roofer is domiciled outside Travis (e.g., a Round Rock or Williamson County LLC doing Austin work) — those stay `unresolved` instead of `candidate`, undercounting the five-state ledger's honesty. Statewide is ~10x the row volume with no change to the `resolved` count (since `resolved` requires an identifier crosswalk, which doesn't exist) — all it buys this run is better `candidate` recall at import cost. Given AD-05/D-1 already fixed Travis scope, this is a documented limitation, not a blocker: record the out-of-Travis-candidate risk in manifest limitations rather than relitigating scope.

**Track A (identity):** Load `9cir-efmm` once in `pipeline/oracle-runtime`, through one adapter (new TS Socrata corporate-registry ingest, same shape as the existing Comptroller/Sunbiz-style ingest already referenced in ADR-0000 §1.1), staged with `ON CONFLICT` upsert keyed on taxpayer number, watermark on `:updated_at` (Socrata), snapshot digest = sha256 of the sorted row set at capture. Single writer (`Loader('travis')`); Track C's business-record transform reads the same loaded rows, never a second fetch. Resolver lives in `query-db-loading-matching`: normalisation rule versioned as code (resolver module with a semver + digest stamped per row, AD-26 pattern), ledger row shape per ADR-0000 §2.4 (`permitKey, rawContractorName, state, matchRule, resolverVersion, registrySnapshotDigest, effectiveOn`), immutable (append, never update in place). `contractor_not_printed` for AC-4 (15,060 permits), `registry_unavailable` for AC-5 — both must short-circuit before the matcher runs, never silently fall through to name=identity. Risk: if the Socrata adapter and the Comptroller ingest both land in the same PR, a reviewer may conflate "official identity load" with "permit load" — keep them as separate adapter registrations (AD-17). Verify: five-state sum = permit total (22,084), 25-row NFR-001 sample, resolver version in manifest `coverage`.

**Track B (BBB):** no live request. Travis profile `roofing-contractors` under the Austin/Travis market URL category is the enrichment target only in spec (not fetched this run, D-2). AC-6 bounds (≤7 requests, ≤1/3s, concurrency 1, `--max-pages 2 --max-profiles 5`); a robots.txt fetch is a precondition check, not a profile/page fetch, so it should NOT count toward the 7 — but since D-2 forbids any new bbb.org request this run, robots.txt is also not fetched live; the stub server must serve both robots.txt and profile responses so the wrapper's own counter is exercised and tested. Linking: BBB status rows join only on `resolved` company id (never a name-match cascade) — with 0 `resolved` expected, expect 0 BBB rows this run, all `blocked` citing the two existing 403 receipts. D-2 enforcement in code: a config value (e.g. `BBB_TARGET=stub`) gates the base URL, asserted in a unit test; CI should grep-fail on `bbb.org` appearing outside the stub-config/evidence files. Blocked shape: `{source_access_status: "blocked", incomplete_reason: "http_403_source_block", evidence: {url, code, time, digest}}`.

**Track C (business/places):** build only if A&D merge by 2026-10-23 12:00 EEST (currently a gap per spec). Wrapper: smallest possible TS CLI step that shells out `elephant-cli` + DuckDB against `scripts/extract-county-places.sql` with `:fips='48453'` bound — the skill's own `extract-overture-places.mjs` isn't bundled, so write a thin equivalent (bbox prefilter via `ST_Intersects`, then exact `ST_Within` against the Travis polygon) rather than reimplementing the SQL. `expected_count` is explicitly null when the Overture release has no stated row estimate, never 0. Risk: if A/D don't merge in time, stub this as a documented gap exactly like Track B.

**Track D (reconcile/roof age):** TCAD id is the fixed merge key everywhere (P0-5) — a lint-level test should assert no merge function accepts two TCAD ids. Contractor clusters merge only where ledger state = `resolved`; with 0 `resolved` expected, expect `merge{entityType:"contractor", inputRecords:N, canonical:N}` (no actual merging) — don't let a reviewer mistake 0 merges for a bug. A-02's Travis profile feeds the estimator the roofing/status classification and basis rules but lacks a `roof_age_basis`/`roof_age_confidence` lexicon carrier (both `no_carrier`) and a close/final-inspection-date column from Austin's own data (`completed_date` is the best available final signal). Estimator commands: `roof-age/estimator.ts` audit dry-run (`--limit 25 --as-of-date <run finishedAt> --source-system travis-austin-permits`) → human review → apply (same flags, no `--limit`) → re-run proving `rowsWritten: 0`; reports land under `pipeline/data/<track>/travis/<jobId>/roof-age-{audit,apply,rerun}.json`. Views comparison: `packages/query-core`'s roof_date derivation is diffed row-for-row against the estimator's ledger output for the 25 audited properties; any mismatch is a blocker before G7 (AC-17/NFR-004 require 25/25).

**All tracks → manifest coverage:** every count is written only by the A-03 manifest builder, reading CLI outputs + capture receipts (never a direct Query DB read), each tagged `derivation` ∈ {`published_rows`,`capture_receipt`,`aggregate_match`} per AD-28. This story computes and hands these numbers to that builder's interface; publication is A-11, out of scope here.

**Order and sharing:** (1) Comptroller load once (shared root for A and C) → (2) Track A resolver (needs the load) → (3) Track D's roof-age half can run in parallel; D's contractor-merge half waits on A's `resolved` ledger → (4) Track B waits on A's `resolved` list (currently empty, stub-only) → (5) Track C business transform reads the same loaded Comptroller rows as A, independent of A's resolver; places ingestion is independent of everything but its own licence gate.

## mew (carriers)

**1. Company legal name / Comptroller taxpayer number / SOS file number / `property_improvement_has_contractor`:** `company.name` is the legal-name carrier. No Texas taxpayer-ID field on `company` — per AD-06/ADR-0002 #1, the taxpayer number carries as `request_identifier` + `source_http_request` on the matched record (accepted fallback, not a gap). SOS file number: not covered in ADR-0002's nine-field verdict table; unconfirmed — treat as the same fallback until re-checked. `property_improvement_has_contractor` exists in the live Property Improvement group schema and is the correct link, written only for `resolved` (confirmed by ADR-0002 #1 — the pilot wrote no such edge since no `resolved` contractors existed).

**2. BBB rating + profile URL:** No carrier. `fact_sheet` has only `full_generation_command` and `ipfs_url` — no rating/grade field, and `company_has_fact_sheet` doesn't exist in the Property Improvement group (only in County). Confirmed against all 159 cached schemas — only `school` and `utility` rating fields exist, no business-rating class. Fallback: AD-25, `bbb_status = not_checked` / `no_lexicon_carrier`.

**3. Comptroller business record:** Travis business records load as `company` records inside the **County** data group. No separate "corporate_registry" lexicon class exists — ADR-0000 §2.2's proposed `corporate_registry` group is aspirational/internal naming, not a confirmed lexicon group; `company` under County is the actual carrier.

**4. Places lexicon group:** No dedicated "place"-named lexicon class in the 159 cached schemas. However, `listPublishedCounties` (live) shows Hillsborough and Polk with a populated `placesTableUrl` — `elephant-cli` does support exporting a places table as a side group in practice, not a classed lexicon entity. Travis isn't in the published catalog yet (`getPlaceQuerySchema("travis")` → `available: false`). The export mechanism exists and is proven elsewhere; Travis's own gate (licence + release) is what's unproven (AC-12/AC-13).

**A-02 carrier recheck:** confirmed correct as recorded. `property_improvement` has `additionalProperties: false` with no name/raw-name field and no candidate/ambiguous/conflicting enum anywhere on `property_improvement`, `company`, or the group. A-02's "no carrier" verdict for both the printed name and the per-permit state stands unchanged.

**Drafted lexicon extension requests** (not filed — PO decision), written to `specs/007-enrich-reconcile/lexicon-extension-drafts.md`: one for the Comptroller taxpayer number (new field) and one for BBB rating/profile URL (new `business_rating` class).

**Caveat:** live lexicon MCP tools (both kit-bundled and legacy) still returned "Internal error" on every call — the same failure mode ADR-0002 recorded on 2026-10-20/21. mew relied on the ADR's byte-for-byte check against the cached schema set (159 schemas, confirmed present) plus one live cross-check (`listPublishedCounties`, which still works).
