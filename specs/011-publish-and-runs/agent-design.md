## oracle (publication, runs)

1. **Manifest builder / sequence changes for full-county scale (5 groups, not 2):**
   - `DataGroup` is currently `"county" | "property_improvement"` only (`pipeline/publish/src/sequence.ts:30`), and `SOURCE_ORDER` in `manifest.ts:37` is hardcoded to exactly Austin+TCAD, enforced by `checkInput`'s exact-match throw (`manifest.ts:334-338`). Both need to become configuration, not a literal union/tuple, or Run 1 at full-county scale throws by design. Widen `DataGroup` to the 5 groups (county, property_improvement, owner, contractor, parcels) and make `SOURCE_ORDER`/coverage keys a per-run profile — owner/contractor/parcels need their own coverage keys (e.g. `parcels_published`, `contractor_resolved/candidate/unresolved` per AD-05's five states).
   - `groupPlan`/`planBuild`/`planUpload` already generalize over `groups: readonly DataGroup[]`, so the six-step fan-out itself scales without change once the 5-group list is passed in.
   - `PART_SIZE_BYTES` (48 MiB) stays; at ~2.95–3.73 GB total this is ~65–80 parts per large group — no code change, but worth re-verifying `export-tables` timing at full-table size, not just the walking-skeleton's 2,380,939-row Austin table.
   - `checkInput` must be extended to the 5 groups' coverage keys and the full source list (Austin permits, TCAD, plus whatever contractor/places sources are in scope) — extend the fixed list, keep it fail-closed, don't loosen it to an unordered "anything goes" check.
   - `groupArtifacts` is already group-agnostic — scales to 5 groups with no change.
   - Confirmed: nothing in `manifest.ts` reads the Query DB directly today (AD-01/AD-28 compliant); keep it that way as groups are added.

2. **Second independent pin (AD-22):** Recommend **Storacha (web3.storage) free tier** (5 GB, Filecoin-backed, independent company/infra from Filebase) over standing up and babysitting a self-run kubo node. A kubo node needs uptime, a public IP/relay and ongoing operator attention for what the story scopes as a one-time durability requirement, not an ops commitment — that's scope creep. Fallback if Storacha's API doesn't script cleanly against the kit's tooling: Pinata's free tier (1 GB), which combined with the GitHub Release CAR copy (already required) still gives three real copies even if Storacha alone can't hold the full archive twice. Don't build new infra; use an existing pinning product.

3. **Filebase free-plan sizing:** Recommend **pin only the newest manifest's live Filebase copy fully, and measure before upgrading** — don't pre-emptively upgrade. Run 1 gets all three copies (Filebase + second pin + Release). Run 2/3 publish only their changed-group CARs to all three copies, so cumulative Filebase usage should stay modest after Run 1. If actual cumulative size exceeds the free 5 GB, use Filebase's paid Starter plan for one month (the story's own edge-case text names this option) rather than unpinning an old run from the primary pin — unpinning technically still satisfies "every previous CID fetchable" via the second pin + Release, but needlessly weakens the durability story for a likely sub-$10/month difference. Record the decision and the measured size in `docs/evidence/A-11-manifest.md` either way.

4. **Incremental run design:** Reuse A-04's existing watermark + content-digest + re-stamp-detection logic (`travis/permits/restamp.ts`-equivalent: ≥50% of window or ≥90% of window within 6h ⇒ bulk re-stamp, delta by content digest) rather than re-deriving it — this directly satisfies FR-006. The real code change is in `manifest.ts`'s `ManifestSourceInput`/`source()`, which today hardcodes `added: records, changed: 0, removed: 0` ("first run: everything is new") — Run 2/3 need explicit `added`/`changed`/`removed` fields supplied by the reconciliation layer's digest comparison. TCAD supplemental and BBB both follow the same zero-delta-with-reason pattern already in the spec's edge cases; recommend the per-run manifest **omits** an unchanged group's artifact entries entirely rather than repeating them, consistent with AD-03's "no re-pointing" philosophy — a consumer finds the group's last real CID via the run chain (`previousManifestCid`), not by re-reading a stale entry. `runs-index.ts`'s `appendRun` is already correctly append-only (throws on duplicate runId/manifestCid) — no change needed there.
   - **Important clarification for the plan (not a business decision, an engineering interpretation):** AC-10 ("same inputs → 0 rows, same CIDs") cannot mean the *manifest* CID is identical run-to-run, since the manifest legitimately records `startedAt`/`finishedAt`, which differ between runs even with zero data change. AC-10 means the **data-group CARs/tables CIDs** (genuinely content-addressed) are identical, which already falls out of `cidOfBytes(jcsBytes(...))` being a pure function of the data. Recommend the plan and test cases state this explicitly so AC-10 is satisfiable as written, rather than leaving an ambiguous "same CIDs" that two testers could read differently.

5. **Anticipated disagreement with machamp:** machamp's Fargate task needs to run "the kit AWS batch mode end to end" unattended, but the current runner (`pipeline/publish/src/upload.ts`, `cli.ts`) is a local, **approval-gated**, two-phase (build-then-upload) interactive CLI flow — `runPublish` (both phases, no human approval) is deliberately not exported today (per CR-A-03 F-4, to preserve the D-8 human-approval gate). oracle's position: an unattended scheduled run should still go through an approval check — just an **automated** approval rule (validate/hash/validate-car/export-tables all succeed), not skip the gate outright — since publishing a bad run against the full 3 GB county is a bigger risk than a pilot, and the manifest-immutability guarantee depends on nothing bad being published in the first place.

## machamp (scheduler)

1. **CDK construct and stack placement:** A new, small stack — `CountyLensSchedulerStack` — as a sixth stack in `infra/src/app.ts`, not folded into Data/Api/Ops. Reasons: OpsStack already owns alarms/budget and depends on Web/Api (AM-02 order); the scheduler has no such dependency, and AD-26/constitution rule 10 says ingestion runs live in one stack, never mixed with serving stacks. Construct: `aws-scheduler` `CfnSchedule` (or the L2 `Schedule` construct) with `state: "DISABLED"`, target = ECS RunTask against a Fargate `TaskDefinition` (no `FargateService` — Scheduler invokes `RunTask` directly, so there's no always-on service and therefore $0 idle cost). Add this stack after Data (for the CID-copy bucket ARN) but with no dependents, so it never blocks the Data→Api→Web→Ops→Cert deploy order.

2. **Fargate task invocation:** Image = the kit's existing AWS-batch-mode container, built via the normal CDK asset pipeline. Entrypoint = the kit's batch-mode CLI entry that runs the full incremental sequence end to end — never the local Restate handler path (AD-26 forbids mixing modes). Inputs via task-definition environment/secrets, never literals: DB credentials as an ECS `Secret` from Secrets Manager (ARN only in CDK code, value supplied by the operator out-of-band, same pattern as `OPERATOR_EMAIL` in ops-stack.ts), bucket/CloudFront names via CloudFormation cross-stack refs from DataStack, and watermark/run state read from wherever oracle's runner persists it (S3 prefix or Postgres) rather than passed as scheduler input, so re-runs stay idempotent.

3. **CDK assertion plan** (new `infra/test/scheduler.test.ts`):
   - DISABLED: `Template.fromStack(...).hasResourceProperties("AWS::Scheduler::Schedule", { State: "DISABLED" })`.
   - Target is this task: assert the schedule's ECS target references this stack's `TaskDefinition` logical id (`Match.objectLike` against a `Fn::GetAtt`/`Ref`, not a literal ARN).
   - No Query DB connection string: a repo-wide grep test over `apps/` and `infra/` source for a Postgres connection-string pattern or a hardcoded host, plus asserting the ECS `Secret`'s `valueFrom` is a Secrets Manager/SSM ARN, never a plaintext `environment` entry.
   - $0 while disabled: assert no `AWS::ECS::Service` exists (only a `TaskDefinition`, which bills nothing until run), no provisioned capacity, and no always-on resource (no NAT/ALB added solely for this stack) — Fargate RunTask and EventBridge Scheduler both bill per-invocation, so "no always-on resource" is the real assertion.

4. **Anticipated disagreement with oracle:** oracle's runner in local/Restate mode likely expects a long-lived local Postgres and durable-workflow server, not a one-shot batch-friendly entrypoint with externally injected secrets and no filesystem state. machamp needs from oracle: (a) does the kit's "AWS batch mode" already exist as a documented containerizable entrypoint, or does oracle need to build one; (b) where does the runner persist watermark state when run as a batch task (Fargate tasks are ephemeral — can't be local disk only); (c) confirmation that batch mode never touches the project's Query DB/VPC (AD-26 implies a separate operator-chosen private Postgres, not the Query DB) — reviewers (donphan, porygon) will check for accidental Query DB reachability from AWS.
